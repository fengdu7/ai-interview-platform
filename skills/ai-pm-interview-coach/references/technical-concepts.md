# AI 产品经理面试：技术概念分类与准备重点

## 先明确：每个概念准备到哪一层

| 优先级 | 准备目标 | 要达到的程度 |
| --- | --- | --- |
| P0 必备 | 能直接用于项目讲解和技术选型 | 一句话解释；举业务例子；说明为什么用、主要代价、如何验证 |
| P1 进阶 | 能接住项目追问，体现问题分析能力 | 知道在链路中的位置；能定位失败原因、比较替代方案 |
| P2 专项 | JD 或真实项目涉及才深入 | 通用岗先知道用途；相关岗位再提升到 P0/P1，并补实现细节 |

主回答统一结构：场景诉求 → 方案取舍 → 效果验证。

你的重点是用技术解释产品决策。例如：“客服需要查经常更新的规则，所以先验证 RAG；代价是知识维护和检索延迟；用真实工单检查检索质量、回答正确性和处理耗时。”面试官追问后，再展开切分、重排、样本和指标口径。

## 一、模型基础：知道模型能做什么、为什么会出错

| 概念 | 优先级 | 一句话理解 | 面试侧重点 |
| --- | --- | --- | --- |
| 大语言模型 LLM | P0 | 从大量数据中学习语言规律，并根据上下文生成输出的模型 | 能生成答案不代表拥有实时事实、业务权限或执行能力；区分模型与完整产品 |
| Token 与分词 Tokenization | P0 | 模型处理文本的基本单元，不等于一个汉字或英文单词 | 影响上下文容量、费用和输出长度；不能固定按“一个字一个 Token”估算 |
| 上下文窗口 Context Window | P0 | 一次处理能容纳的输入与输出规模约束 | 历史、资料、工具结果会占空间；装得下不代表能准确使用所有信息，具体限额按模型确认 |
| 训练与推理 Training / Inference | P0 | 训练调整模型参数，推理使用已有参数完成任务 | 区分开发时训练投入和上线后调用投入；用户聊天通常不会自动更新基础模型参数 |
| 幻觉 Hallucination | P0 | 输出看似可信、但缺乏依据或不符合事实的内容 | 先归因：资料缺失、检索错误、理解错误或生成错误；低温度和 RAG 都不能保证零幻觉 |
| 预训练与后训练 | P1 | 预训练建立基础能力，后训练进一步改善指令遵循、偏好或任务表现 | 理解能力来源，区分通用能力与业务适配；不用背完整训练流水线 |
| Temperature / Top-p | P1 | 调节输出采样方式的参数 | 影响随机性而非事实真实性；低温不等于绝对确定，各模型的支持方式不同 |
| 参数量、Dense 与 MoE | P1 | 参数量描述规模；MoE 对不同输入激活部分专家网络 | 不用参数量直接判断效果、速度或成本；区分总参数量与激活参数量 |
| Transformer / Attention | P2 | 一类利用注意力机制处理序列关系的模型架构 | 通用岗理解“根据上下文建立关联”即可；模型平台岗再补结构、计算和长上下文问题 |
| 推理模型与推理预算 | P1 | 部分模型可投入更多计算来处理复杂任务 | 比较任务收益、等待时间、成本；不能把解释更长当作推理更可靠 |

## 二、Prompt 与上下文：把任务说清楚、把信息给对

| 概念 | 优先级 | 一句话理解 | 面试侧重点 |
| --- | --- | --- | --- |
| Prompt Engineering | P0 | 通过指令、示例、约束和输出要求组织任务 | 先定义任务与验收标准；区分 Prompt 问题和知识、工具、模型能力问题 |
| 指令层级与角色消息 | P1 | 系统、开发者、用户等信息在产品中承担不同作用 | 明确信任边界，不能把网页或工具返回内容当作高优先级指令；具体角色按接口确认 |
| Zero-shot / Few-shot / ICL | P1 | 不给或给少量示例，让模型在当前上下文中完成任务 | 示例是否代表真实任务、是否一致；ICL 不等于更新模型参数的微调 |
| 结构化输出 / JSON Schema | P0 | 约束输出的字段和结构，便于程序消费 | 格式合法不等于内容正确；还要检查字段语义、业务规则、拒绝和错误情况 |
| Context Engineering | P1 | 管理每一步实际提供给模型的信息、状态与工具结果 | 重点是相关性、时效性、权限与容量；不是把所有文档都塞进去 |
| 长上下文与压缩 / 摘要 | P1 | 直接放入更多材料，或压缩历史以控制容量 | 信息遗漏、摘要失真和成本；与检索方案比较，不把窗口大小等同记忆能力 |
| 任务拆解与分步求解 | P1 | 把复杂任务拆成可检查的子任务 | 哪一步可验证、失败后怎样恢复；展示可检查的依据和结果，不把长思维文本当正确性证明 |

## 三、RAG 与知识工程：让回答建立在合适的资料上

RAG 的基础流程：资料处理 → 建索引 → 检索 → 筛选或重排 → 组织上下文 → 生成与核验。权限、版本和引用核验需要系统实现，不是用了 RAG 就自动具备。Microsoft 官方说明

| 概念 | 优先级 | 一句话理解 | 面试侧重点 |
| --- | --- | --- | --- |
| RAG 检索增强生成 | P0 | 先找相关资料，再让模型结合资料回答 | 适合外部知识、更新频繁的资料等；代价是检索、知识维护、延迟和错误传播 |
| 文档解析、清洗与元数据 | P1 | 把文档整理成可检索内容，并保留来源、时间、权限等属性 | PDF 表格、标题和上下文是否丢失；错误资料进入系统会污染后续答案 |
| Chunk / Chunking 文本切分 | P0 | 把长文切成检索单元 | 太小可能缺上下文，太大可能带噪声；按文档结构和任务评测，不能套固定最优长度 |
| Embedding 向量表示 | P0 | 把内容转换成可计算语义相似度的向量 | 看领域、语言与真实检索效果；相似不等于正确，维度更多也不必然更好 |
| 向量库与向量索引 | P1 | 存储向量并支持相似内容检索 | 数据规模、更新、过滤、延迟、部署成本；向量库不是完整知识库产品 |
| 关键词检索 / BM25 | P1 | 根据词项匹配等信号检索文档 | 型号、订单号、专有词等精确匹配场景；理解为何有时比纯语义检索更适合 |
| 混合检索 Hybrid Search | P1 | 组合关键词与向量等检索结果 | 兼顾精确词和语义；评测融合后的收益与成本，不默认一定优于单一路径 |
| Recall / Top-k 检索候选 | P0 | 先取若干可能相关的资料，供后续使用 | k 大可能找全但增加噪声与延迟；区分“召回阶段”和“召回率指标” |
| Rerank 重排序 | P1 | 对候选结果重新打分、排序 | 主要改善排序，不能凭空补回候选集中缺失的资料；额外增加计算开销 |
| Query Rewrite / 多路查询 | P1 | 对用户问题进行改写、拆分或补充检索表达 | 能否保持原意、解决模糊问题；警惕查询漂移和多次检索成本 |
| Grounding 与引用核验 | P0 | 检查答案是否有资料支撑，以及引用是否真正支持结论 | 有引用不等于答案正确；区分忠于资料与资料本身真实、最新 |
| 知识更新、版本与访问过滤 | P0 | 确保取回当前有效且当前用户有权看的资料 | 旧政策失效、用户权限变更和缓存隔离；不能只在生成后遮盖敏感内容 |
| GraphRAG / 多跳检索 | P2 | 利用实体关系或多轮检索整合跨资料信息 | 关系推理和跨文档任务是否确有需求；考虑抽取质量、维护成本和简单方案基线 |

## 四、Agent 与工具：从“回答”到“完成任务”

这里采用实用区分：Workflow 主要按预定义路径编排，Agent 让模型动态决定部分步骤与工具使用。两者可组合；复杂度应由任务决定。Anthropic 架构说明

| 概念 | 优先级 | 一句话理解 | 面试侧重点 |
| --- | --- | --- | --- |
| Workflow 与 Agent | P0 | 前者偏固定流程，后者偏动态决策与执行 | 稳定流程是否需要开放决策；比较可控性、成功率、延迟和维护成本 |
| Tool / Function Calling | P0 | 模型提出结构化工具调用，由应用校验并执行 | 模型提出调用不代表执行成功；看选工具、填参数、权限、执行结果与回传 |
| API、HTTP 与 JSON | P0 | 系统调用外部能力和交换结构化数据的常见方式 | 能理解请求、响应、错误码和数据结构；知道模型、工具、后端各负责什么 |
| Planning / ReAct | P1 | 拆解目标，并交替选择动作、读取执行反馈 | 何时需要动态规划；设置步数、时间与成本上限，防止重复动作或死循环 |
| 状态管理与 Memory | P1 | 保存任务进度，按需持久化用户或历史信息 | 会话上下文、任务状态和长期记忆不同；关注更新、遗忘、权限和串用户风险 |
| MCP | P1 | AI 应用连接外部工具、资源等能力的一种协议 | 理解 Host、Client、Server；连接标准化不等于自动具备业务判断、权限和安全保障 |
| 路由、串行与并行编排 | P1 | 把任务交给合适模型或工具，并安排依赖关系 | 可并行部分与前后依赖；增加复杂度是否带来质量或时延收益 |
| Human-in-the-loop 人工介入 | P0 | 在关键或高风险环节让人确认、处理或接管 | 介入时机、人工负担和接管信息；不要把所有问题一律转人工 |
| 多 Agent 协作 | P2 | 多个角色或执行单元协作完成任务 | 是否真需要职责分工；考虑交接损耗、重复工作、一致性与成本 |
| Skill / 工具 / MCP 的区别 | P1 | Skill 常封装任务说明与流程，工具提供动作接口，MCP 规范部分连接方式 | 名称与实现因平台而异；不能把三者当同义词，也不能把“装了 Skill”当效果保证 |

MCP 概念以官方架构文档为准；协议与平台会更新，通用岗优先理解职责边界，不背固定消息格式。

## 五、训练与适配：什么问题值得用训练解决

| 概念 | 优先级 | 一句话理解 | 面试侧重点 |
| --- | --- | --- | --- |
| SFT 监督微调 | P0 | 用任务示例训练模型，使输出更符合期望 | 适合稳定任务、格式和行为适配等；需要数据与评测，不会自动同步新的业务事实 |
| Prompt / RAG / 微调的选型 | P0 | 分别从任务表达、外部知识、参数适配等角度改善效果 | 判断主因后选择，可组合使用；比较效果、数据、更新频率、成本与维护 |
| 数据标注与训练 / 验证 / 测试集 | P0 | 给数据定义标签或参考答案，并分离训练、调参与最终检验 | 标注规范、一致性、代表性、重复样本与泄漏；同一案例改写后跨集合也可能泄漏 |
| LoRA / PEFT | P1 | 通过训练较少参数等方式进行高效适配 | 降低训练资源需求，但不保证效果；部署和推理开销仍取决于实现 |
| RLHF / 偏好对齐 / DPO | P1 | 利用偏好信息改善模型行为，不同方法优化路径不同 | 偏好数据来源、评价标准与偏差；不能简单认为“人喜欢”就等于事实正确 |
| 蒸馏 Distillation | P1 | 用教师模型的输出或能力指导学生模型学习 | 以质量、覆盖和成本验证是否值得；学生可能继承教师错误 |
| 过拟合与分布变化 | P1 | 在熟悉样本上表现好，却未必适应新用户、新业务 | 测试集分层、时间外验证、线上监控和持续更新 |
| Loss / Mask / 学习率 / Batch / Epoch | P2 | 训练目标、参与计算的位置及训练过程参数 | 仅高技术或训练平台岗深入；普通应用岗理解它们影响数据学习与训练稳定性即可 |

LoRA 的低秩更新与冻结基础权重机制参考 Hugging Face 官方概念说明。本节优先级是应用产品岗建议，不是算法岗要求。

## 六、评估体系：证明“好在哪里”，并定位问题

| 概念 | 优先级 | 一句话理解 | 面试侧重点 |
| --- | --- | --- | --- |
| 离线评测与在线评测 | P0 | 离线用固定任务测试，在线观察真实使用效果 | 离线好不保证线上好；上线前后分别看什么，如何发现分布差异 |
| 评测集与 Bad Case | P0 | 用代表性任务和失败案例持续检验系统 | 覆盖典型、边界、异常场景；开发调试集与独立验收集分开，避免只针对已知题优化 |
| Rubric 评分标准 | P0 | 把“好答案”拆成可观察、可复核的标准 | 正确性、完整性、可用性等如何判定；明确底线项、合格条件与标注分歧处理 |
| Accuracy / Precision / Recall / F1 | P0 | 描述分类或检索等任务不同方面的表现 | 先定义任务、正例和统计单元；漏报与误报代价不同，不能统称“准确率” |
| Recall@k / Precision@k / 排序指标 | P1 | 检查前 k 条结果找全、找准和排对的程度 | 需要可靠相关性标注；检索好不代表最终答案好，排序岗再深入 MRR、NDCG |
| 正确性 / 忠实性 / 相关性 | P0 | 分别看事实对不对、是否符合给定依据、是否回答所问 | 三者可能不一致；引用原文但原文过期，可能忠实却不正确 |
| 端到端任务成功率 | P0 | 用户任务完整达到约定验收条件的比例 | 分母与成功标准清楚；工具成功或某一步正确不等于完整任务成功 |
| 人工评审与 LLM-as-a-Judge | P1 | 由人或模型按标准评判结果 | 模型评审也会偏差；用人工样本校准，检查位置偏差、同源偏好和一致性 |
| 回归测试与版本对比 | P1 | 检查修改后旧能力是否退化，并比较版本 | 尽量固定任务和评测条件；只改一处便于归因，记录模型、提示词、知识版本 |
| A/B 测试与因果判断 | P0 | 用可比较的实验组和对照组估计方案影响 | 随机化单位、样本量、实验周期和护栏指标；简单前后对比不能排除其他影响 |
| 样本量、置信区间与显著性 | P1 | 判断估计的不确定性，以及差异是否可能来自随机波动 | 小样本不能过度外推；统计显著不等于业务收益足够大；重复任务不等于独立用户 |
| 技术指标、业务指标与护栏 | P0 | 分别看系统表现、用户/经营结果和不可牺牲的约束 | 把模型准确率连到任务完成、效率、成本等；效率提高不能以质量或风险恶化为代价 |

常用口径速记

- 分类 Precision = TP / (TP + FP)；Recall = TP / (TP + FN)。先说清正例是什么，例如“应拦截的违规内容”。
- F1 = 2 × Precision × Recall / (Precision + Recall)，不是在所有业务中都应优先优化的指标。
- 检索 Recall@k = 前 k 条中相关结果数 / 标注的全部相关结果数；Precision@k = 前 k 条中相关结果数 / k。若实际返回不足 k 条，需要事先约定处理方法。
- 端到端成功率 = 达到全部必要验收条件的任务数 / 约定统计范围内的有效发起任务数。故障、超时和未完成如何计入，要在看结果前确定。
- 每个合格任务成本 = 统计范围内模型、工具和人工等总成本 / 合格任务数；应包含失败尝试的消耗，零合格任务时不能给出正常有限成本值。
## 七、上线与工程协作：效果之外，能否稳定交付

| 概念 | 优先级 | 一句话理解 | 面试侧重点 |
| --- | --- | --- | --- |
| 延迟、TTFT 与端到端耗时 | P0 | 分别看各环节等待、首个 Token 到达及完整任务用时 | 首字快不等于任务完成快；定位检索、生成、工具与人工修改的耗时 |
| P50 / P95 与吞吐 / 并发 | P1 | 看典型与尾部延迟，以及系统处理量和同时承载量 | 平均值会掩盖慢请求；并发不等于吞吐，结合负载与服务目标评测 |
| Token 费用与任务总成本 | P0 | 调用费用只是任务成本的一部分 | 输入输出、重试、检索、工具和人工成本一起算；省工时不自动等于减少现金支出 |
| 流式输出、异步任务与取消 | P1 | 逐步显示输出，或后台执行并反馈进度 | 用户感知、真实完成状态、取消是否生效；不能提前把“处理中”说成“已完成” |
| 缓存与失效 | P1 | 复用部分计算或结果来减少延迟与成本 | 区分前缀缓存和答案缓存；注意资料更新、用户权限、命中率及错误复用 |
| 超时、重试、幂等与降级 | P0 | 处理失败，并避免同一动作重复产生副作用 | 重试扣款、发消息、下单可能重复执行；明确次数上限、幂等标识和人工兜底 |
| 路由与大小模型分工 | P1 | 按任务难度、风险和资源要求分配模型 | 用任务分层评测选择，而非默认全部使用最强或最便宜模型 |
| 日志、Trace 与可观测性 | P1 | 记录跨步骤的输入、决策、调用、时延和结果 | 能定位哪一环失败；关联版本与任务，同时控制日志中的敏感信息 |
| 灰度发布、回滚与 SLA / SLO | P1 | 分批上线并定义服务承诺或内部目标 | 放量条件、异常阈值、回滚方案；质量、错误率、延迟与成本共同监控 |
| API 服务与私有化部署 | P1 | 使用外部服务，或在受控基础设施运行系统 | 数据控制、可用性、算力、升级维护和总成本；私有化不是天然更便宜或更安全 |
| 量化、KV Cache、Batching | P2 | 从精度表示、生成中间状态复用和批量调度改善资源效率 | 通用岗理解资源与质量权衡；模型服务平台岗再深入吞吐、显存与尾部延迟 |

## 八、安全与权限：哪些能力必须由系统约束

| 概念 | 优先级 | 一句话理解 | 面试侧重点 |
| --- | --- | --- | --- |
| Prompt Injection 提示注入 | P0 | 不可信输入试图改变系统原有任务或规则 | 文档、网页、工具输出都可能带入攻击；区分数据与指令，仅加一句 Prompt 不足以保证安全 |
| 身份认证与权限控制 | P0 | 确认用户是谁，以及可以读取、修改或执行什么 | 最小权限、租户隔离、工具侧校验；模型不能自行决定放宽权限 |
| 隐私、脱敏与数据留存 | P1 | 控制哪些数据可采集、发送、记录和保留 | 梳理数据流、服务配置和访问范围；不能仅凭“企业版”或“本地”标签作判断 |
| Guardrails、拒答与安全兜底 | P1 | 用规则、检测、校验和人工机制限制不合适输出或动作 | 误拒与漏放如何取舍；结合业务风险分级，不追求盲目全放开或全拦截 |
| 沙箱、执行隔离与审计 | P2 | 限制执行环境，并追踪发生过的操作 | Coding / Computer-use / 执行型 Agent 岗重点；重点是边界、审批与可追溯性 |

## 九、多模态专项：目标产品涉及再提高优先级

| 概念 | 优先级 | 一句话理解 | 面试侧重点 |
| --- | --- | --- | --- |
| 多模态 / VLM | P2 | 联合处理文本、图像等不同形式的信息 | 图片理解、空间关系、小字读取的真实能力；用业务样本验证，不能只看演示 |
| OCR 与文档理解 | P2 | 识别文字，并进一步还原结构与语义 | 表格、扫描件、版式和手写误差；识字正确不等于字段抽取正确 |
| ASR / TTS | P2 | 语音转文字 / 文字转语音 | 口音、噪声、专有词、时延和可懂度；语音产品再补端到端语音模型 |
| VAD、端点检测与打断 | P2 | 判断是否在说话、何时说完，以及如何打断播报 | 避免抢话或等待过长；实时语音产品升为必备 |
| 文生图 / 图像编辑 / Diffusion | P2 | 按条件生成或修改图像；扩散是其中一类方法 | 指令遵循、一致性、编辑范围、生成耗时；不把所有图像生成模型都等同扩散模型 |
| 视频时序一致性与音画同步 | P2 | 判断连续帧、主体动作和声音是否协调 | 不只看单帧美感；看长时一致性、可控编辑、生成失败与成本 |

## 十、搜索推荐与数据分析专项：电商、内容、增长岗位重点

| 概念 | 优先级 | 一句话理解 | 面试侧重点 |
| --- | --- | --- | --- |
| 召回、粗排、精排与重排 | P2 | 从大量候选中逐级筛选、排序和调整 | 各层效果与效率分工；电商、内容推荐岗提升到 P0 |
| 推荐特征与冷启动 | P2 | 用用户、物品和上下文信息匹配需求，并处理新用户/新内容 | 数据稀缺时如何做；不把生成式导购直接等同推荐系统 |
| CTR、CVR 与多目标优化 | P2 | 通过点击、转化等指标观察业务，同时兼顾多种目标 | 点击高不代表价值高；退货、留存、利润、供给质量需结合场景看 |
| 埋点、事件与指标口径 | P0 | 用可追踪事件描述用户行为并计算指标 | 谁触发、何时触发、统计单位、去重和分母；AI 对话还要定义任务起止与重试 |
| 漏斗、分群与 Cohort | P1 | 看用户在哪一步流失，以及不同人群、不同进入时间的表现 | 用来定位问题；相关关系只是线索，需要实验或其他证据进一步验证 |
| SQL 与数据核验 | P1 | 从业务数据中提取和检查分析所需的信息 | 聚合、连接、去重、时间窗口与空值；避免一对多连接造成重复计数 |

## 十一、最容易混淆的九组概念（时间有限，看这个就可以）

| 对比 | 一句话分清 | 容易说错的地方 |
| --- | --- | --- |
| Prompt vs RAG vs 微调 | 改任务表达、提供外部资料、调整参数适配是不同干预位置 | 把三者说成永远三选一；微调可以学到知识，但不适合作为自动实时更新机制 |
| 长上下文 vs RAG | 一个偏直接提供材料，一个偏先筛选所需材料 | 认为上下文长就不需要检索、权限管理或版本管理 |
| Embedding vs Rerank | 前者常用于表示与候选检索，后者对候选重新排序 | 认为两者都是“换个大模型就好” |
| Agent vs Workflow | 动态决策与预定义编排的程度不同 | 认为每个聊天机器人都是 Agent，或 Agent 一定优于 Workflow |
| Tool Calling vs MCP | 一个涉及提出工具调用，另一个规范连接与能力暴露 | 认为接上 MCP 就能自动完成任务或保证安全 |
| 结构化输出 vs 正确答案 | 一个检查形式，一个检查事实与业务语义 | JSON 能解析就宣布任务成功 |
| 检索召回率 vs 任务成功率 | 一个看资料是否找全，一个看用户任务是否完成 | 用检索提升直接证明业务收益 |
| 模型准确率 vs 业务收益 | 一个是技术表现，一个是任务与经营结果 | 未验证就宣称准确率提升带来了收入增长 |
| 离线评测 vs A/B 实验 | 一个检验固定样本表现，一个估计真实条件下的方案影响 | 用少数展示案例、简单前后对比代替实验结论 |

## 十二、按岗位调整重点

| 岗位方向 | 提升为重点的知识 | 可以后置的内容 |
| --- | --- | --- |
| 通用 AI 应用产品 | 场景选型、Prompt、RAG/微调区别、工具调用、评测、成本与兜底 | 训练数学、推理框架、底层协议报文 |
| 企业知识库 / AI 客服 | 文档处理、检索链路、知识时效、引用、权限、拒答、转人工 | 无业务需求的多 Agent 或 GraphRAG |
| Agent / 自动化平台 | 状态、编排、工具、MCP、幂等、人工确认、Trace、执行安全 | 与执行任务无关的生成模型训练细节 |
| 模型平台 / 高技术产品 | 数据工程、训练与对齐、LoRA、量化、推理效率、服务 SLO | 不能只停留在概念层；需补真实系统与工程约束 |
| 创作工具 / 多模态 | 内容评分、可控编辑、多模态专项、创作流程、单位合格作品成本 | 与产品无关的语音或推荐细节 |
| 电商导购 / 搜索推荐 | 召回排序、商品知识、实时库存价格、业务链路、实验与多目标优化 | 不能只研究 LLM 生成效果，忽略交易与履约 |
| 数据分析型 AI 产品 | SQL、指标口径、语义层、查询校验、数据权限、分析可复核性 | 只强调“能自动画图”，忽略数据正确性 |

“升为重点”以 JD、团队职责和你要讲的真实项目为准。平台名字、模型版本、上下文限额、单价和 SDK 参数容易变化，面试前再核对，不作为固定概念死背。

## 十三、时间有限：按这五步准备

- 先讲明白一个系统。 画出“用户输入 → 信息/权限 → 检索或工具 → 模型 → 校验/兜底 → 结果与监控”，说明哪些环节真的存在。
- 再掌握关键选型。 练习规则还是 AI、Workflow 还是 Agent、RAG 还是微调、强模型还是小模型。每题都能说出场景、约束与验证方式。
- 接着讲清效果。 为自己的项目准备一套业务目标、技术指标、评测样本和上线条件；数据只用真实结果。
- 准备三个失败案例。 至少覆盖知识/检索错误、模型输出错误、工具/工程错误，说明怎样定位与修复。
- 最后补岗位专项。 根据 JD 将相关 P2 项升级，不平均用力。
如果只先抓一组知识：LLM 与幻觉、Token 与上下文、Prompt、RAG、Embedding 与切分、SFT、Agent/Workflow、工具调用、评测集与指标、成本延迟、权限与失败兜底。 先把这些串成一个项目故事，再扩展细节。

## 十四、用六道题检查是否真的理解

| 自测题 | 回答应该包含什么 |
| --- | --- |
| 为什么选择 RAG 而不是微调？ | 当前问题、资料更新与来源要求、方案代价、相同任务上的验证方法 |
| RAG 回答错了，你从哪里查？ | 原资料 → 解析/版本/权限 → 检索 → 重排/上下文 → 生成；逐层找证据 |
| 什么时候不需要 Agent？ | 路径是否固定、是否需要动态判断、简单方案能否达标，以及复杂度成本 |
| 模型选对工具，但任务仍失败，怎么办？ | 参数、授权、执行、返回解析、状态、重试和最终业务验收 |
| 准确率提高了，为什么用户不满意？ | 评测是否代表真实任务；是否忽略耗时、交互负担、失败代价和实际完成率 |
| 什么时候能上线、什么时候能扩大投入？ | 质量底线、真实任务结果、成本与风险；先验证用户价值，再验证增长和经营收益，按项目调整 |

面试表达模板

我们要解决的是【用户在场景中的问题】，主要约束是【质量／更新／延迟／成本／权限】。

所以优先用【方案】，因为【关键匹配理由】；主要代价是【代价】。

我会用【代表性任务】检查【关键指标】。如果没有达标，先定位【可能的失败环节】，再决定是否调整方案。
