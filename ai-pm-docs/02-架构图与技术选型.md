## 二、分层说明（用文字讲清这张图）

架构可以拆成 6 层，PM 记这个分层就够了：

### 第 1 层 · 客户端
- **React SPA 前端**：面试中心、简历库、知识库、语音面试等页面。
- 与后端有三种通信方式：**REST（普通请求）、SSE（流式问答）、WebSocket（语音面试实时音频）**。

### 第 2 层 · 接入层
- **Spring Boot REST API**：统一响应 `Result<T>`、限流 `@RateLimit`、参数校验、全局异常处理。

### 第 3 层 · 业务层（4 个模块）
- `resume`（简历）、`interviewschedule`（面试安排）、`knowledgebase`（知识库）、`voiceinterview`（语音面试）。

### 第 4 层 · AI 能力层（产品的灵魂）
| AI 能力 | 作用 |
|---|---|
| **LLM 调用** | Spring AI 统一接入 OpenAI 兼容模型 |
| **RAG 检索** | pgvector 向量检索 + 查询改写 + TopK，让 AI 基于文档回答 |
| **语音能力** | DashScope（Qwen3）的 ASR（语音识别）+ TTS（语音合成） |
| **语音评估引擎** | 分批评估 + 结构化输出 + 二次汇总 + 降级兜底，面试后异步打分 |

### 第 5 层 · 异步任务层
- **Redis Stream**：简历分析、知识库向量化、出题、面试评估等长耗时 LLM 任务，全部走异步队列，支持重试、恢复、防重。

### 第 6 层 · 数据层
| 存储 | 存什么 |
|---|---|
| **PostgreSQL + pgvector** | 业务数据 + 向量（1024 维，HNSW 索引，COSINE 距离） |
| **Redis** | 面试会话缓存 + Stream 消息队列 |
| **S3 兼容存储（MinIO/RustFS）** | 简历文件、知识库文件的原始文件 |

## 四、选型的真正逻辑：复杂度成本 vs 能力

> **先纠正一个 PM 常踩的坑**：RAG、微调、直接调大模型三者**不是对立关系**，各解决不同问题——RAG 解决知识边界和幻觉，微调解决风格和领域能力，直接调解决通用问答。别说出"RAG 优于直接调大模型"这种话。

技术选型里，产品视角真正要理解的不是"为什么选 A 不选 B"，而是**每类选型背后都是「复杂度成本 vs 能力」的权衡**：

- **PostgreSQL + pgvector（而非独立向量库）**：这个产品向量量级不大，HNSW 索引 + COSINE 距离够用，少维护一个组件比极致检索性能更值钱。
- **Redis Stream（而非 Kafka）**：异步任务量不大，Stream 足够；解耦后分析/向量化甚至可以用别的语言实现。

> 两条选型的共同点是**"够用就精简"**——不是 pgvector 比 Milvus 强，也不是 Stream 比 Kafka 强，而是这个产品的规模下，精简架构的收益大于极致能力。

> **PM 的思考角度**：面试官追问"如果你负责，你会做同样选择吗"，你要给的是**基于规模和场景的判断**（这个量级下我认同精简），而不是背"谁比谁好"。

## 五、架构的两个关键特征（一句话讲清）

- **异步化**：简历分析、向量化、出题、面试评估都是长耗时 LLM 任务，全部走 Redis Stream 异步，前端轮询状态。
- **实时语音链路**：语音面试通过 WebSocket 实时传输音频，ASR/TTS/LLM 一体化，支持自动断句、回声防护。
